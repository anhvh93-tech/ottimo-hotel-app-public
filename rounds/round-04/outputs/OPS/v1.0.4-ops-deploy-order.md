### 1.1 `infra/server/bin/deploy.sh`
- Bước `switch` cũ (một lệnh `dc up … api worker web`) tách thành **hai bước có tên riêng**, mỗi bước một lệnh `dc up --wait`:
  - `switch-worker`: `dc up … worker`, rồi kiểm worker **còn chạy** sau 3 giây (`worker_stays_up`). Worker không có healthcheck, nên `--wait` trả về ngay khi container chạy. Kiểm này bắt worker chết lúc khởi động **trước khi** api đổi.
  - `switch-api`: `dc up … api web`. `web` vẫn chờ `api` healthy qua `depends_on`, như trước.
- Thứ tự:
  - deploy thường: `switch-worker` → `switch-api`. Worker mới chạy trước khi api mới nhận lệnh. Api mới có thể tạo job outbox mà worker cũ không biết, nên worker mới phải lên trước.
  - `--rollback`: `switch-api` → `switch-worker`. Api mới (cùng web mới) dừng trước, rồi worker cũ mới chạy. Như vậy worker cũ không gặp job do api mới **vừa** tạo.
  - `--remove-orphans` chỉ nằm ở lệnh `up` đầu tiên của mỗi chiều.
- `restore_previous` (deploy lỗi sau khi container đã đổi) dùng thứ tự quay lui: `api web` của bản trước, rồi `worker` của bản trước. Nếu `api web` bản trước **không** lên healthy thì **không** chạy worker cũ, mà ghi `WARNING: previous api/web did not come back healthy – worker left as is`. Lý do: api mới có thể vẫn đang trả lời.
- Tên bước mới `switch-worker` và `switch-api` thay cho `switch`. CI chỉ thấy `failed (step=<tên>)` (`deploy-from-ci.sh` giữ `a-z-`, không đổi). Lỗi ở `switch-worker` nghĩa là api/web **chưa** đổi.
- **Không thêm dòng log `[deploy …]` nào.** Lượt chạy thành công vẫn in đúng 6 dòng như các tờ lệnh INV (R4 v1.0.1, runbook v1.0.3). Test (i) và (k) khóa điều này.
- Không đổi: guard production, digest, `appconfig`, `roles`, `migrate` (vẫn chạy trước mọi đổi container), `smoke`, `record`.

## 4. Giả định
- **G1:** `docker compose up --wait <svc>` chỉ đổi service được nêu và các service nó phụ thuộc (ở đây là `postgres`, đã chạy, không bị tạo lại). `worker` không phụ thuộc `api`, nên `up … api web` không đụng worker. Diễn tập 5.0 trên staging xác nhận điều này trên compose thật: không có container `worker` nào được tạo lại ở bước `switch-api`.
- **G2:** 3 giây đủ để thấy worker chết lúc khởi động (ví dụ lỗi cấu hình, thiếu bảng). Worker chết muộn hơn thì vẫn bị bước `smoke` bắt (`sleep 5` + kiểm lại `RestartCount` của **cùng** container). Từ bản sửa 04/11 (mục 7), kiểm không còn dựa vào trạng thái `running` lúc lấy mẫu. Giờ thật từ `up` tới dòng `worker started` ghi vào biên bản 5.0 (ARC P402-02).
- **G3:** Đổi tên bước `switch` thành `switch-worker`/`switch-api` không làm gãy gì. Không có script nào so tên bước. Các runbook cũ (v1.0.2) nhắc `switch` theo nghĩa chung. Runbook v1.0.4 và README (P4-04) dùng tên mới.

- **FB-R4-ARC-OPS-P402-01 (Major):** `worker_stays_up` (lấy mẫu `ps --status running`) thay bằng `worker_ok`:
